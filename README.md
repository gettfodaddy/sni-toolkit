# sni-toolkit

Подбор SNI-донора для Xray Reality-нод. Два инструмента, разного назначения —
не путать, где что запускать:

| Скрипт | Что делает | Где запускать |
|---|---|---|
| `sni-verify.sh` | Проверка 1 домена или списка кандидатов: TLS1.3, H2, post-quantum, сертификат, CDN, HTTP-статус, маршрут, задержка. Один файл, ничего доп. не ставится | **На самой Reality-ноде**, для которой подбираешь донора |
| `sni-scan.sh` | Массовый скан IP/CIDR/списка/каталога ссылок → короткий список кандидатов (TLS1.3+H2). Требует Go | **Локально / на одноразовой VM**, НЕ на боевой ноде |

## Установка одной командой — только `sni-verify.sh`

Это тот инструмент, который гоняешь прямо на ноде, поэтому он специально
сделан однофайловым и без зависимостей (только bash/curl/openssl/sed/awk —
есть на любой VPS из коробки; `mtr` — по желанию, без него просто пропустится
один пункт отчёта). Список кандидатов по странам встроен прямо в файл, никаких
дополнительных `.txt` рядом не нужно.

Разместил `sni-verify.sh` у себя (см. варианты хостинга ниже) — на ноде,
два равноценных способа запустить:

**Вариант 1 — сохранить как команду** (удобно, если будешь гонять повторно):

```bash
curl -Ls https://<твой-хостинг>/sni-verify.sh -o /usr/local/bin/sni-verify \
  && chmod +x /usr/local/bin/sni-verify
sni-verify -auto
```

**Вариант 2 — одна строка, без сохранения файла на диск** (пайп сразу в bash,
как у manual32):

```bash
wget -qO- https://censorcheck.tlab.pw | bash
```

Без аргументов скрипт сам уходит в режим `-auto` — ровно то же самое, что
`sni-verify -auto` из варианта 1, просто без промежуточного файла. Передать
флаги в этом виде запуска можно через `bash -s --`:

```bash
wget -qO- https://censorcheck.tlab.pw | bash -s -- -f candidates.txt -out result.csv
```

Оба варианта делают одно и то же: сам определит IP/страну ноды, прогонит
стартовых кандидатов и выдаст таблицу (с живым прогресс-баром по ходу
сканирования) с лучшим по задержке, вместе с готовым `dest`/`serverNames`
для вставки в конфиг. `censorcheck.tlab.pw` — просто пример имени хостинга
для варианта 2, замени на свой домен/поддомен, где реально лежит файл (см.
варианты хостинга ниже — годится любой из них, в том числе raw-ссылка с
GitHub, для пайпа это не важно).

### Где разместить сам файл, чтобы curl работал

- **Публичный репозиторий на GitHub** (проще всего) — положи `sni-verify.sh`
  в свой репозиторий, копируй прямую ссылку на raw-файл:
  `https://raw.githubusercontent.com/<юзер>/<репо>/<ветка>/sni-verify.sh`.
  В самом скрипте нет ничего секретного (ни доменов твоей инфры, ни
  токенов) — публиковать именно этот файл отдельно от остального
  Cyphra-репозитория безопасно, даже если основной репозиторий приватный.
- **GitHub Gist** (публичный) — то же самое, ссылка на raw purposes ещё короче.
- **Свой сервер / панель**, как сделан сам manual32.online — просто отдать
  файл статикой по HTTPS (nginx `location /sni-verify.sh { alias
  /path/to/sni-verify.sh; }` или вообще любая папка со статикой). Плюс —
  полностью под твоим контролем и не привязано к GitHub; минус — сам следишь
  за доступностью хостинга.
- **Приватный репозиторий GitHub** — тоже можно, но тогда `curl` в одну
  команду не сработает без токена (raw-URL приватного репо требует
  `Authorization: Bearer <token>` в заголовке) — либо публикуй только этот
  один файл отдельно (вариант выше), либо добавляй токен в команду и следи
  за его сроком жизни.

После правки скрипта — просто перезалей файл на тот же URL, следующий `curl`
на любой ноде подтянет свежую версию. Обновлять команду install/chmod не
нужно, meняется только содержимое файла по тому же адресу.

## Быстрый старт (полный, с `sni-scan.sh`)

```bash
git clone <твой репозиторий> sni-toolkit
cd sni-toolkit
chmod +x sni-scan.sh sni-verify.sh

# Вариант А — с нуля, без готового списка: нода сама себя проверит по
# встроенным стартовым кандидатам под свою страну:
ssh user@node
./sni-verify.sh -auto -out result.csv

# Вариант Б — полный массовый поиск, когда стартового списка мало:
# 1) Массовый поиск кандидатов — С ЛОКАЛЬНОЙ МАШИНЫ, не с ноды:
./sni-scan.sh build                                    # один раз, собирает RealiTLScanner
./sni-scan.sh -url https://launchpad.net/ubuntu/+archivemirrors -thread 20 -out candidates.csv
awk -F, 'NR>1{print $3}' candidates.csv | sort -u > candidates.txt   # домены из CSV в текстовый список

# 2) Перенеси candidates.txt на боевую ноду, дальше — точечная проверка ОТТУДА:
scp candidates.txt user@node:~/
ssh user@node
sni-verify -f candidates.txt -out final.csv             # таблица + CSV, сортируй/смотри сам
sni-verify www.example.com                              # подробный отчёт по конкретному финалисту
```

`-auto` и `-f`/batch-режим сами предлагают лучшего по задержке кандидата из
тех, кто дотянул до вердикта ГОТОВ — готовый `dest`/`serverNames` для вставки
в конфиг. Перед вставкой всё равно прогони его отдельно
(`sni-verify <домен>`) — там полный отчёт с mtr и сертификатом.

## Почему два отдельных этапа, а не один скрипт

1. **Массовый скан тысяч хостов — заметный паттерн трафика.** Официальный
   README RealiTLScanner прямо предупреждает: *"running the scanner in the
   cloud may cause the VPS to be flagged"*. Гонять его с боевой Reality-ноды —
   плохая идея вдвойне: (а) сам скан может привлечь внимание, (б) это та же
   нода, которую ты не хочешь светить лишний раз.
2. **Финальная проверка (латентность/маршрут) должна идти именно с ноды.**
   Донор с идеальным TLS-профилем, но битым или медленным маршрутом именно с
   твоего конкретного VPS (Selectel и т.п.) — бесполезен для конкретно этого
   сервера. Это ровно то, что мы разбирали на примере ru-9/ConnectTimeout: DNS
   и ICMP могут быть в порядке, а TCP:443 — зависать. `sni-verify.sh` замеряет
   `time_connect` отдельно от DNS и предупреждает именно на этот паттерн.

## Что проверяет `sni-verify.sh`

1. DNS + TCP:443 + TLS connect timing (ловит паттерн "ICMP ок, TCP:443 виснет").
   Задержка в таблице/отчёте — это время TCP+TLS-рукопожатия целиком
   (`%{time_appconnect}`, целые миллисекунды), а не голый TCP-connect
   (`%{time_connect}`) в сырых секундах, как было раньше — из-за этого цифры
   выглядели неадекватно маленькими (`0.002550s`). Если донор реально лежит
   на CDN-грани рядом с нодой (см. п.6 CDN) — миллисекунды честно могут быть
   однозначными, это не баг
2. TLS 1.3 — обязательное условие для Reality
3. HTTP/2 (ALPN h2) — обязательное условие для Reality
4. Post-quantum key exchange (X25519MLKEM768) — **информационно, не провал**,
   см. предупреждение ниже про Xray-core версии
5. Сертификат: issuer, SAN, размер в байтах (>3500 байт нужно, если планируешь
   включать `mldsa65` — post-quantum подпись самого Reality-сертификата)
6. CDN-фронтинг (Cloudflare/Akamai/Fastly/CloudFront) — предупреждение, не провал
7. HTTP-статус / редиректы
8. Маршрут именно с этого сервера (`mtr`, с фолбэком на `traceroute`)
9. ASN/страна донора (best-effort, через ip-api.com, не критично при недоступности)

Вердикт: **ГОТОВ** / **ПРОВЕРЬ** / **НЕ ГОДИТСЯ** — но это не единственный
источник истины, читай предупреждения по пунктам 4-6 сам, финальное решение
за тобой.

`donors-seed.txt` — отдельный файл, нужен только `sni-scan.sh -url`
(страницы-каталоги ссылок для краулера, массовый поиск с локальной машины).
Список кандидатов для `sni-verify.sh -auto` живёт прямо внутри самого
скрипта (функция `country_candidates()`) — редактируй его там же.

## ⚠️ Post-quantum (X25519MLKEM768) — обязательно прочитай перед выбором

Здесь легко ошибиться в обе стороны, поэтому вынесено отдельно.

- **Xray-core сервер < 26.9.8**: REALITY-клиент автоматически подхватывает
  post-quantum key exchange, ЕСЛИ его поддерживает донор. Старые клиентские
  библиотеки без PQ-совместимого uTLS-профиля на PQ-доноре могут не собрать
  handshake — в этом случае донора БЕЗ post-quantum выбрать безопаснее.
- **Xray-core сервер >= 26.9.8** (актуально прямо сейчас, сентябрь 2026):
  сервер сам **требует** X25519MLKEM768 key share в ClientHello от клиента —
  независимо от того, что умеет донор. Это защита протокола, добавленная
  апстримом (commit `8cdf7bf9c7f0`, "reject outdated/strange Client Hello
  that doesn't have X25519MLKEM768 before optional X25519"). Отсюда следует
  **важная и срочная вещь, не про донора**: клиентские приложения на базе
  sing-box/mihomo с профилем `HelloChrome_Auto`, если их uTLS ещё не обновили
  под этот key share, получат `reality verification failed` /
  тихий fallback-редирект на боевых серверах 26.9.8+. Это ломает подключение
  клиентам независимо от выбранного донора.
  **Перед тем как обновлять Xray-core на нодах до 26.9.8+, проверь, что
  используемые клиентские приложения (или их конкретные версии) реально
  умеют слать этот key share** — иначе рискуешь массово отвалить действующих
  пользователей в момент обновления сервера, а не в момент смены SNI.
  Источники по теме — issues в sing-box/mihomo/LxBox, ссылки внизу.

## Про `sni-pick` с manual32.online

Изначально не смог ни скачать, ни прочитать этот скрипт для проверки (домен
не в allowlist сетевой политики этого окружения, fetch-инструмент вернул
404) — но Ivan прислал содержимое напрямую, и вот разбор.

**Код чистый.** Три внешних вызова: `api.ipify.org` (узнать свой IP),
`ip-api.com` (геолокация по IP), и сами кандидаты через `curl -s -o
/dev/null` (только заголовки/статус, ничего не скачивает и не исполняет).
Ничего не тянет и не запускает дополнительно, никаких скрытых payload'ов.
Само по себе безопасно ставить и гонять.

Две вещи в нём оказались реально полезными и удобнее, чем было у меня —
перенёс прямо в `sni-verify.sh`:

1. **Список кандидатов по стране ноды** — вместо того чтобы начинать с
   пустого места, сразу пул проверенных национальных брендов под геолокацию
   IP. Это флаг `-auto` (сам определяет IP через `api.ipify.org`, страну —
   через `ip-api.com`, парсинг через `sed`, без `jq` — тот не на каждой
   минимальной VPS стоит из коробки, а тут важно, чтобы совсем без доп.
   установок). Список кандидатов встроен в сам файл (функция
   `country_candidates()`), а не лежит рядом отдельным `.txt` — так весь
   `sni-verify.sh` остаётся одним самодостаточным файлом для curl-инсталла.
2. **Редирект — не всегда провал.** У меня раньше ЛЮБОЙ 3xx считался
   проблемой; в sni-pick редирект бракуется, только если уводит на ДРУГОЙ
   домен (bare-домен → www того же сайта — это норм, а не "легенда
   рассыпалась"). Поправил ту же логику у себя (см. п.7 отчёта).

Не стал копировать сам файл `sni-pick.sh` в этот репозиторий: в шапке
скрипта — "личная копия... передача третьим лицам запрещена". Домены
компаний по странам — не объект авторского права (это просто факт "такая-то
компания работает в такой-то стране"), поэтому список данных переиспользовал,
а код скрипта — нет.

Инструмент из другого, менее проверяемого источника, чем официальный
`XTLS/RealiTLScanner`, на котором построен `sni-scan.sh` — так что при
прочих равных предпочтение ему, но после чтения кода sni-pick тоже не вижу
причин не пользоваться.

## Продвинутый уровень: SNI-to-DNS consistency check

Даже идеальный по TLS1.3/H2/маршруту донор не защищает от продвинутой
техники детекции: цензор пассивно логирует пары (SNI, IP назначения) во
время handshake, затем офлайн резолвит домен из SNI и сверяет с IP, куда
реально ушло соединение. У любого "одолженного" донора (чужой SNI, но
соединение идёт на IP твоей ноды) это несоответствие видно — независимо от
того, насколько близко географически или по ASN донор к ноде ("сосед по
подсети" не помогает, см. обсуждение в issue #668 ниже). Единственный способ
закрыть эту дыру полностью — модель "steal yourself": владеть доменом,
держать на нём реальный сайт, и резолвить его DNS на IP самой ноды (`target`
указывает на `localhost`). Это отдельный, более трудоёмкий заход
(понадобится реальный домен + реальный контент на ноде), сюда не входит —
но стоит знать, что это следующий уровень, если когда-нибудь понадобится.
